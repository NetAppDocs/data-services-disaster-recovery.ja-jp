= NetApp Disaster Recoveryについて学ぶ
:hardbreaks:
:allow-uri-read: 
:icons: font
:imagesdir: ../media/get-started/


[role="lead"]
クラウドへの災害復旧は、サイトの停止やデータ破損イベントからワークロードを保護するための、回復力があり対費用効果の高い方法です。NetApp Disaster Recoveryは、NetAppストレージで実行されているVMwareおよびKubernetesワークロードの災害復旧ワークフローを自動化する、クラウドベースの災害復旧サービスです。Disaster Recoveryを使用すると、次のワークロードを保護できます：

* *VMwareワークロード*：NFSベースのワークロードと、iSCSIおよびFC用のVMware vSphere仮想マシンファイルシステム（VMFS）データストア。これらを以下のいずれかに複製できます：
+
** Amazon Elastic VMware Service (EVS) と Amazon FSx for NetApp ONTAP。詳細については、link:../reference/evs-deploy-guide-introduction.html["Amazon Elastic VMware Service および Amazon FSx for NetApp ONTAP を使用した災害復旧の概要"]を参照してください。
** VMware Cloud (VMC) on AWS とAmazon FSx for NetApp ONTAP
** Azure VMware Solution とNetApp Cloud Volumes ONTAP （iSCSI）（プライベートプレビュー）
** Google Cloud VMware Engine（GCVE）とGoogle Cloud NetApp Volumes
** 別のオンプレミスのNFSおよび/またはVMFSベース（iSCSI/FC）のVMware環境（ONTAPストレージ搭載）


* *Kubernetesワークロード*：Tridentで管理されるONTAPストレージを使用する、OpenShift仮想化環境を含むオンプレミスのKubernetesクラスタで実行されるアプリケーション。Trident Protectを使用してこれらを保護し、別のKubernetesクラスタにレプリケートします。


災害復旧は、ONTAPのすべてのストレージ効率の利点を維持しながら、VMware VMとそれに関連するディスク上のOSイメージ、およびKubernetesアプリケーションを保護するために、統合されたネイティブVMwareオーケストレーションまたはTrident Protectオーケストレーションを備えたONTAP SnapMirrorテクノロジを使用します。災害復旧では、これらの技術を災害復旧サイトへのレプリケーション転送手段として利用します。これにより、プライマリサイトとセカンダリサイトの両方で、業界最高水準のストレージ効率（圧縮と重複排除）を実現できます。

image:../use/evs-console-architecture.png["災害復旧の構成要素を示す図"]



[[netapp-console]]
== NetApp Console

災害復旧は、NetApp Consoleからアクセスできます。

NetApp Consoleは、オンプレミスとクラウド環境全体にわたるエンタープライズ グレードのNetAppストレージとデータ サービスの集中管理を提供します。NetAppデータ サービスにアクセスして使用するには、コンソールが必要です。管理インターフェースとして、1 つのインターフェースから多数のストレージ リソースを管理できます。コンソール管理者は、企業内のすべてのシステムのストレージとサービスへのアクセスを制御できます。

NetApp Console の使用を開始するためにライセンスやサブスクリプションは必要ありません。ストレージ システムや NetApp データ サービスへの接続を確保するためにクラウドに Console エージェントをデプロイする必要がある場合にのみ料金が発生します。ただし、Console からアクセスできる一部の NetApp データ サービスは、ライセンスまたはサブスクリプションが必要です。

詳細はこちら https://docs.netapp.com/us-en/console-setup-admin/concept-overview.html["NetApp Console"]。



[[benefits-of-using-disaster-recovery]]
== 災害復旧を利用するメリット

災害復旧には、以下の利点があります：

* vCenterおよびKubernetesクラスタの検出、ならびに複数のポイントインタイム リカバリ処理を使用したアプリケーションの復旧における、簡素化されたユーザエクスペリエンス。
* 運用コストが削減され、最小限のリソースで災害復旧計画を作成および調整できるため、総所有コストが削減されます。
* 運用を中断しない仮想フェイルオーバー テストによる継続的な災害復旧の準備。実稼働ワークロードに影響を与えることなく、DR フェイルオーバー プランを定期的にテストできます。
* IT 環境の動的な変化と災害復旧計画でそれに対応する能力により、価値実現までの時間が短縮されます。
* 導入および保守が必要な仮想サーバーアプライアンス (VSA) を必要とせずに、 ONTAPと VMware の両方のバックエンドオーケストレーションを通じて、ストレージレイヤーと仮想レイヤーの両方を同時に管理できます。
* Trident Protectのオーケストレーションと、同じONTAP SnapMirrorテクノロジを使用した、Kubernetesワークロード向けのアプリケーション中心の保護。リソース変換を使用すると、フェイルオーバー時にワークロードを復旧環境に適応させることができます。
* VMware の DR ソリューションは大量のリソースを必要とする場合があります。多くの DR ソリューションは、VSA を使用して VMware 仮想レイヤーで VM を複製しますが、これによりコンピューティング リソースがさらに消費され、 ONTAPの貴重なストレージ効率が失われる可能性があります。ディザスタ リカバリではONTAP SnapMirrorテクノロジーが使用されるため、 ONTAPのネイティブ データ圧縮と重複排除の効率性をすべて備えた永久増分レプリケーション モデルを使用して、実稼働データストアから DR サイトにデータを複製できます。




[[capabilities-of-disaster-recovery]]
== 災害復旧の機能

ディザスタリカバリでは、以下の目標を達成するために、いくつかのNetAppテクノロジをフルに活用できます：

* SnapMirrorレプリケーションを使用して、オンプレミスの運用サイトにある VMware アプリケーションをクラウドまたはオンプレミスの災害復旧リモート サイトにレプリケートします。
* SnapMirrorレプリケーションとTrident Protectを使用して、KubernetesアプリケーションをデスティネーションKubernetesクラスタにレプリケートします。
* VMwareワークロードを元のサイトから別のサイトに移行します。現在、Kubernetesワークロードの移行はサポートされていません。
* フェイルオーバーテストを実施します。VMwareワークロードの場合、このサービスは一時的な仮想マシンを作成します。Disaster Recoveryは、選択したスナップショットから新しいFlexCloneボリュームを作成し、そのFlexCloneボリュームをバックエンドとする一時データストアがESXiホストにマッピングされます。このプロセスでは、オンプレミスのONTAPストレージやAWSのFSx for NetApp ONTAPストレージの物理容量を追加で消費することはありません。元のソースボリュームは変更されず、レプリカジョブは災害復旧時でも継続できます。Kubernetesワークロードのフェイルオーバーをテストし、その後テストリソースをクリーンアップすることもできます。
* 災害時には、必要に応じてプライマリサイトを災害復旧サイトにフェイルオーバーします。VMwareワークロードの場合、災害復旧サイトは、Amazon FSx for NetApp ONTAPを使用するVMware Cloud on AWS、またはONTAPを使用するオンプレミスのVMware環境にすることができます。Kubernetesワークロードの場合、レプリケーション計画のデスティネーション クラスタにフェイルオーバーします。
* 災害が解決したら、要求に応じて災害復旧サイトからプライマリ サイトにフェールバックします。
* 効率的な管理のために、VM、データストア、またはKubernetesリソースを論理的なリソースグループにグループ化します。
* Kubernetesワークロードの場合、リソース変換を使用してフェイルオーバー中にアプリケーションを復旧環境に適応させ、スナップショット前またはスナップショット後のスクリプトを使用してアプリケーションの静止状態と再開を管理します。


image:../use/evs-use-cases.png["災害復旧のユースケースを示す図"]


NOTE: VMwareワークロードの場合、Disaster Recoveryの外部にあるvSphere ServerでvSphereサーバを設定する必要があります。

次のライセンス タイプを使用できます。

* 30 日間の無料トライアルにサインアップしてください。
* Amazon Web Services (AWS) Marketplace、Azure Marketplace、またはGoogle Cloud Marketplaceで従量課金制（PAYGO）サブスクリプションを購入します。このライセンスにより、長期契約の義務なしに、固定容量の保護ライセンスを購入できます。
* BYOL (Bring Your Own License) は、 NetApp の営業担当者から取得したNetAppライセンス ファイル (NLF) です。ライセンス シリアル番号を使用して、 NetApp Consoleで BYOL をアクティブ化できます。


すべてのNetAppデータ サービスのライセンスは、 NetApp Consoleのサブスクリプションを通じて管理されます。  BYOL を設定すると、コンソールでサービスのアクティブなライセンスを確認できます。

Disaster Recoveryは、保護されたONTAPボリュームでホストされているデータ量に基づいてライセンスされます。このサービスは、保護対象のVMをそれぞれのvCenterデータストアにマッピングすることで、ライセンスの対象となるボリュームを決定します。各データストアは、ONTAPボリュームまたはLUNでホストされます。そのボリュームまたはLUNについてONTAPが報告する使用容量が、ライセンスの判定に使用されます。Kubernetesワークロードの場合も、ライセンスは同じ方法で計算されます。

保護ボリュームには、多数の仮想マシンをホストできます。中には、災害復旧リソースグループに含まれないものもあるかもしれません。いずれにせよ、そのボリュームまたはLUN上のすべての仮想マシンが消費するストレージは、ライセンスの最大容量に対して使用されます。


NOTE: 災害復旧の料金は、少なくとも1つのVMまたはKubernetesリソースにレプリケーションプランが設定されている場合、ソースサイトのデータストアの使用容量に基づいて計算されます。フェイルオーバーされたデータストアの容量は、許容容量には含まれません。BYOLの場合、データが許容容量を超えると、追加の容量ライセンスを取得するか、NetApp Consoleでライセンスをアップグレードするまで、サービスでの操作が制限されます。

災害復旧のライセンス設定の詳細については、link:../get-started/dr-licensing.html["災害復旧ライセンスの設定"]を参照してください。

[[how-disaster-recovery-works]]
== 災害復旧の仕組み

Disaster Recoveryは、NetApp ConsoleのSoftware as a Service（SaaS）環境から利用できるサービスです。Disaster Recoveryは、オンプレミスサイトからAmazon FSx for ONTAPまたは別のオンプレミスサイトにレプリケートされたワークロードをリカバリできます。VMwareワークロードの場合、このサービスは、SnapMirrorレベルからのリカバリ、VMware Cloud on AWSへの仮想マシンの登録、およびVMwareのネットワーク仮想化およびセキュリティプラットフォームであるNSX-Tでの直接的なネットワークマッピングを自動化します。この機能は、すべてのVirtual Machine Cloud環境に含まれています。

災害復旧は、非常に効率的なレプリケーションを提供し、ONTAPの永久増分スナップショットの効率性を維持するONTAP SnapMirrorテクノロジを使用しています。SnapMirrorレプリケーションにより、アプリケーションと整合性のあるスナップショットコピーが常に同期され、フェイルオーバー後すぐにデータが使用可能になることが保証されます。

image:dr-architecture-diagram-70-2.png["災害復旧サービスインフラストラクチャのアーキテクチャを示す図"]

災害発生時、このサービスは、SnapMirror関係を解除してデスティネーションサイトをアクティブにすることで、別のオンプレミスVMware環境またはVMCでVMware仮想マシンを復旧するのに役立ちます。

* このサービスを使用すると、仮想マシンを元のソースの場所にフェールバックすることもできます。
* 元の仮想マシンを中断することなく、災害復旧フェールオーバー プロセスをテストできます。テストでは、ボリュームのFlexCloneを作成して、仮想マシンを分離されたネットワークに復旧します。
* フェールオーバーまたはテスト フェールオーバー プロセスでは、仮想マシンを復元するための最新 (デフォルト) または選択したスナップショットを選択できます。


*Kubernetesワークロード*

Kubernetesワークロードの場合、Disaster RecoveryはTrident Protectを使用して、OpenShift仮想化環境を含む、Kubernetesクラスタ上で実行されているアプリケーションを保護します。このサービスは、SnapMirrorを使用して、NetApp TridentがONTAPストレージにプロビジョニングする永続ボリュームをレプリケートします。Trident Protectは、クラウドストレージターゲットであるAppVaultにKubernetes保護データを保存します。災害が発生した場合は、デスティネーション クラスタにフェイルオーバーし、災害が解決したあとに元のソースクラスタにフェイルバックできます。Kubernetesワークロードのフェイルオーバー、フェイルバック、およびフェイルオーバーテストは、VMwareワークロードと同じ手順で行われます。

*災害復旧の構成要素*

Disaster Recoveryには以下のコンポーネントが使用されます：

* * NetApp Console*: 災害復旧計画を管理するためのユーザー インターフェイス。  NetApp Consoleを使用すると、オンプレミス環境とクラウド環境全体でレプリケーション プラン、リソース グループ、フェイルオーバー操作を作成および管理できます。
* *Consoleエージェント*：クラウドでホストされるネットワーク、またはオンプレミスのVMware環境で実行される軽量のソフトウェアコンポーネントです。NetApp Consoleと通信し、オンプレミス環境とディザスタリカバリサイト間のデータのレプリケーションを管理します。Consoleエージェントは、VMware環境内の仮想マシンにインストールされます。Kubernetesワークロードの場合、Consoleエージェントは同様の方法でKubernetesクラスタと通信します。
* *ONTAPストレージクラスタ*：ONTAPストレージクラスタは、VMwareおよびKubernetesワークロードをホストする主要なストレージシステムです。ONTAPストレージクラスタは、災害復旧計画の基盤となるストレージインフラストラクチャを提供します。Disaster Recoveryは、ONTAPストレージAPIを使用して、オンプレミスアレイや、Amazon FSx for NetApp ONTAPなどのクラウドベースのソリューションといったONTAPストレージクラスタを管理します。
* *vCenter サーバー*: VMware vCenter は、VMware 環境の管理サーバーです。 ESXi ホストとそれに関連付けられたデータストアを管理します。コンソール エージェントは VMware vCenter と通信して、オンプレミス環境と災害復旧サイト間のデータのレプリケーションを管理します。これには、 ONTAP LUN とボリュームをデータストアとして登録すること、VM を再構成すること、VM を起動および停止することが含まれます。
* *KubernetesクラスタとTrident Protect*：Kubernetesワークロードの場合、Trident Protectは、Disaster Recoveryが保護する各Kubernetesクラスタにインストールおよび登録されます。Kubernetesクラスタをサイトとして追加すると、Disaster Recoveryによって、そのクラスタへのTrident Protectのインストールと登録の手順が案内されます。


*災害復旧保護ワークフロー*

レプリケーション プランがリソース グループに割り当てられると、Disaster Recovery はリソース グループとプラン内のすべてのコンポーネントの検出チェックを実行し、プランをアクティブ化できるかどうかを確認します。

このチェックが成功した場合、Disaster Recovery は次の初期化手順を実行します。

. ターゲット リソース グループ内の各 VM について、ホスティング VMware データストアを識別します。
. 見つかった VMware データストアごとに、ホスティングしているONTAP FlexVol volumeまたは LUN を識別します。
. 見つかった各ONTAPボリュームと LUN について、ソース ボリュームと宛先サイトの宛先ボリュームの間に既存のSnapMirror関係があるかどうかを判断します。
+
.. 既存のSnapMirror関係が存在しない場合は、新しい宛先ボリュームを作成し、保護されていない各ソース ボリューム間に新しいSnapMirror関係を作成します。
.. 既存のSnapMirror関係がある場合は、その関係を使用してすべてのレプリケーション操作を実行します。




ディザスタリカバリによってすべての関係が作成および初期化された後、スケジュールされたバックアップごとに、サービスは次のデータ保護手順を実行します。

. 「アプリケーション整合性」としてフラグ付けされた各仮想マシンについて、VMware Toolsを使用して、サポートされているアプリケーションをバックアップ状態にします。
. 保護された VMware データストアをホストするすべてのONTAPボリュームの新しいスナップショットを作成します。
. SnapMirror更新操作を実行して、これらのスナップショットを宛先ONTAPクラスタに複製します。
. 保持されたスナップショットの数がレプリケーション プランで定義された最大スナップショット保持期間を超えているかどうかを確認し、ソース ボリュームと宛先ボリュームの両方から不要なスナップショットを削除します。




[[supported-protection-targets-and-datastore-types]]
== サポートされている保護対象とデータストアの種類

*サポートされているデータストアの種類* Disaster Recoveryは、以下のデータストアの種類をサポートしています：

* ONTAPクラスタ上に存在するONTAP FlexVolボリューム上でホストされる NFS データストア。
* iSCSI または FC プロトコルを使用した VMware vSphere 仮想マシン ファイル システム (VMFS) データストア


Kubernetesワークロードの場合、ディザスターリカバリーは、ONTAPストレージ上のNetApp Tridentを通じてプロビジョニングされた永続ボリュームを保護します。

*サポートされている保護対象*

* VMware Cloud (VMC) on AWS とAmazon FSx for NetApp ONTAP
* 別のオンプレミスのNFSベースのVMware環境（ONTAPストレージ使用）またはオンプレミスのFC/iSCSI VMFS環境
* Amazon Elastic VMware サービス
* Azure VMware Solution とNetApp Cloud Volumes ONTAP （iSCSI）（プライベートプレビュー）
* Google Cloud VMware Engine（GCVE）とGoogle Cloud NetApp Volumes
* Trident が管理する ONTAP ストレージを使用する Kubernetes クラスター（Trident Protect で保護）




[[terms-that-might-help-you-with-disaster-recovery]]
== 災害復旧に役立つ可能性のある用語

災害復旧に関連するいくつかの用語を理解しておくと役立つかもしれません。

* *データストア*: ファイル システムを使用して VMDK ファイルを保持する VMware vCenter データ コンテナー。一般的なデータストアの種類は、NFS、VMFS、vSAN、vVol です。ディザスタ リカバリでは、NFS および VMFS データストアがサポートされます。各 VMware データストアは、単一のONTAPボリュームまたは LUN でホストされます。ディザスタ リカバリは、 ONTAPクラスタに存在するFlexVolボリュームでホストされる NFS および VMFS データストアをサポートします。
* *レプリケーション プラン*: バックアップの実行頻度とフェイルオーバー イベントの処理方法に関する一連のルール。プランは 1 つ以上のリソース グループに割り当てられます。
* *目標復旧ポイント (RPO)*: 災害発生時に許容できるデータ損失の最大量。  RPO は、レプリケーション プランのデータ レプリケーションの頻度またはレプリケーション スケジュールで定義されます。
* *復旧時間目標（RTO）*：災害からの復旧に許容される最大時間。RTOはレプリケーション計画で定義され、DRサイトにフェイルオーバーしてすべてのVMまたはアプリケーションを再起動するのにかかる時間です。
* *リソースグループ*：複数の仮想マシン、データストア、またはKubernetesリソースを単一の単位として管理できるようにする論理コンテナ。仮想マシンは、一度に1つのリソースグループにしか所属できません。保護したいアプリケーションやワークロードごとにリソースグループを作成できます。
* *サイト*：通常、1つ以上のvCenterクラスタまたはKubernetesクラスタ、およびONTAPストレージをホストする物理データセンターまたはクラウドロケーションに関連付けられた論理コンテナ。
* *AppVault*：Kubernetesワークロードの場合、Trident ProtectがKubernetesの保護データを保存するクラウドストレージターゲット。
* *Trident Protect*：Disaster RecoveryがKubernetesアプリケーションを保護するために使用するNetAppソフトウェア。
